# PERF-1 — kb-mode performance numbers and budgets (2026-10-22)

`NEXT_CYCLES_2026-10-22.md` item PERF-1. Numbers for RC-1's gates 3 and 83.

**Machine.** The sandbox: 4 vCPU Intel Xeon @ 2.10 GHz, 15 GB RAM, Python 3.12.3, Node 22.22.0.
**Setup.** The e2e:kb backend (`frontend/e2e/kb-env/serve-api.sh`): demo off, `UNIMATCH_KNOWLEDGE_MODE=kb`, no
search provider, no browser tier, a scratch SQLite database migrated by `alembic upgrade head` holding the 501-row
catalogue (500 seed + 1 curated-only), the network guard on; uvicorn and the worker as `run.sh --with-worker` starts
them, on port 8199. KB v22: 98 entries, 95 with verified data (`kb_cs_bachelor.json` 1,127,836 bytes +
`kb_imported_dev.json` 90,195 bytes). HTTP over loopback with `httpx`, one warm-up request, then 20 timed.

## 1. `GET /api/universities` in kb mode (the knowledge block per row)

`limit=500` is refused (422): the route caps `limit` at 100. The whole catalogue is therefore measured as the walk an
API client makes, six pages of 100 (offset 0…500), and a single page beside it.

| Request (20 timed each) | before PERF-1 p50 / p95 | after p50 / p95 |
|---|---|---|
| `?limit=100` (one page) | 61.3 / 139.8 ms | **32.6 / 49.7 ms** |
| `?limit=100&offset=0…500` (all 501 rows, six requests) | 460.1 / 564.2 ms | **232.0 / 367.2 ms** |
| `?verified=true&limit=100` (all 95 kb rows) | 64.3 / 197.0 ms | **28.7 / 45.7 ms** |
| `?limit=100&profile_id=…` (CS-bachelor demo profile) | 84.7 / 228.8 ms | **48.0 / 75.8 ms** |
| `?verified=true&limit=100&profile_id=…` | 90.6 / 224.3 ms | **48.9 / 79.0 ms** |

p95 is the noisy figure here (single-digit outliers to ~190 ms on a shared sandbox); p50 is the stable one.

**Hotspots found and fixed** (cProfile of the route, five requests of one page):

1. *The university table read twice per request*: once by the route for `catalogue_total`/`kb_total`/`countries`,
   again inside `retrieve`. `retrieve(..., catalogue=rows)` now takes the rows already loaded; the result does not
   depend on their order. Route time 99 → 62 ms per request in-process.
2. *`KnowledgeBase.by_domain` scanned every KB entry* for each of the ~406 catalogue rows outside the KB, on every
   request (`kb_total` counts all 501): ~2,000 calls and ~290,000 suffix comparisons per five requests, then 45 % of
   the route's time. It now answers from an index of official domains built on first use (rebuilt if `entries` is
   replaced or changes size), with the scan's rule kept: the first entry in `entries` order whose domain is the host
   or a parent of it. Route time 62 → 33 ms per request in-process.

The KB itself is not parsed per request (`routes_universities._knowledge_base` is an `lru_cache`), and there is no
query per row: a page of 1 and a page of 100 issue the same statements, one of them on `universities`.

**Output identical.** 240 variants of the route (query × country × verified × offset × with/without profile) dumped
before and after in kb mode and in live mode: SHA-256 `801ce91a…` (kb) and `b888ba57…` (live) unchanged.
`seed_demo.py` output byte-identical apart from its first line (fresh profile and run ids).

## 2. `load_knowledge_base` (cold)

A fresh interpreter per sample, imports excluded, the two committed files read and merged: **p50 16.6 ms, p95 22.2
ms, max 23.6 ms** over 20 processes. The route reads it once per process.

## 3. The e2e:kb nine-university run, end to end

The journey's API steps (`kb-journey.spec.ts` `beforeAll`): `POST /api/runs` with the nine universities (Stanford,
ETH, KTH, Kyoto, Fudan, Oxford, Edinburgh, Sheffield, Groningen), wait for `awaiting_user_decision`, approve all nine,
`collect-documents`, wait for a checklist and `completed`. Five repetitions against the server above:

| Phase | p50 | max |
|---|---|---|
| research run (POST → settled) | 1.39 s | 1.48 s |
| approve + documents (→ completed) | 0.66 s | 1.34 s |
| **total** | **2.07 s** | **2.50 s** |
| of which the worker's own time (`jobs.started_at → finished_at`): research | 0.66 s | 0.91 s |
| documents | 0.26 s | 0.35 s |

The rest is queue wait: the worker polls every `worker_poll_seconds` = 1.0 s. No page is read and nothing is sent to a
search provider. `npm run e2e:kb` on the same tree: **8 passed (1.2 min)**, the whole browser journey in en/ru/kk.

The timed budgets are 4–5× today's numbers on this machine, for a slow CI runner under `pytest -n 4`; the bundle size is
deterministic, so its ~18 % headroom is for ordinary growth only. As the item says: a budget that fails on CI is
reported with its number, not loosened. Raise the bundle budget on purpose, with the new number in gate 3.
