# Аудит алгоритма поиска: 500 университетов, 10 экспертов

Статус: завершены все 10 экспертных заданий — 500 уникальных записей, по 50 на эксперта. Распределение по позиции в списке с шагом 10 дало каждой группе университеты из всего диапазона 500. Агенты работали волнами, максимум по три одновременно. Исполнитель каждой группы указан в manifest.json.

Исходная версия приложения:144881b. Аудит выполняется в отдельной ветке task/top500-expert-audit; изменения касаются только отчётов и воспроизводящих скриптов. PR41 и опубликованный сайт этим аудитом не обновляются.

## Что проверяется

Каждый эксперт импортирует полный каталог в отдельную базу SQLite в памяти:500 seed-записей плюс один университет из курируемого реестра. Это сохраняет реальные совпадения и неоднозначности между университетами. Затем эксперт проверяет свои50 записей настоящими функциями импорта и поиска, исследует код по своей специализации и сохраняет индивидуальный результат для каждой записи.

Это открытый инженерный аудит, а не слепой экспертный эксперимент. Источники вступительных требований не читались заново: live_checked=false. Seed-цены, баллы экзаменов и домены не получают статус подтверждённых фактов. Моделирование ответов сайтов отдельно отмечено как synthetic. Все500 университетов уже использованы для диагностики; их нельзя объявлять новым независимым набором для проверки гипотез.

## Приоритеты по итогам десяти групп

1. Подтверждать принадлежность сайта университету более надёжно. Синтетический заголовок с названием университета на постороннем сайте проходит существующую проверку; совпадение названия само по себе недостаточно. Нужны реальные положительные и отрицательные страницы, проверенные независимо.
2. Передавать явный контекст выбранной программы в оценку применимости требований. Синтетический неправильный programme/degree при совпадающем intake может стать hard filter; прохождение такого claim через существующие защитные проверки адаптеров в реальном прогоне ещё не доказано.
3. При запросе полного названия ставить точное совпадение выше совпадений города и подстроки. На500 запросах воспроизведены29 неправильных первых позиций; альтернативная сортировка исправляет их в локальном эксперименте.
4. Согласовать страны и регионы между поиском и итоговой оценкой. Retrieval знает регионы и алиасы, а country utility сравнивает строковые названия. Утверждённые формулы и веса менять для этого не требуется.
5. Разделить лимиты установления сайта, поиска программы и проверки фактов; измерить резерв времени для позднего поискового этапа. Сохранить неизвестные результаты, ошибки провайдера и состояние не начатого исследования отдельно.

6. Сохранять диагностику при таймауте и явно отмечать университеты, до которых исследование не дошло. В моделировании эти состояния теряются или выглядят одинаково.
7. Различать временный HTTP 429 и подтверждённое исчерпание квоты. Повторяющийся отказ сейчас расходует все шесть попыток. Остановка должна учитывать тип отказа и сохранять найденные страницы.
8. Переиспользовать проверенные маршруты как подсказки с датой, областью применимости и происхождением. При чтении кэша сохранять способ получения страницы: в моделировании browser превращается в http.
9. Отдельно измерять факты с подтверждённой цитатой, применимостью и актуальностью. Существующий reference recall имеет более узкое назначение, прямо оговорённое его проверкой.

Все 11 объединённых кандидатов перечислены в candidates.json. Это список кандидатов на отдельные исправления. Для каждого нужны отрицательные контроли, одинаковый бюджет сравнения и независимая проверка. Совпадение нескольких экспертных наблюдений не заменяет живой проверки.

Проверка покрытия предназначена для завершённой кампании. Она требует10 завершённых групп, ровно50 результатов в каждой, все500 уникальных seed_id без пропусков, индивидуальные tests/observations/risk и live_checked=false.
