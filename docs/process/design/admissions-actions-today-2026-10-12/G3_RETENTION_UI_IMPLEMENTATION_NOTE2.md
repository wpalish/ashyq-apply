## 3. Finite removal algorithm and recovery boundaries

1. **Read/display only.** `readAdmissionsActionsRecovery`325–326 and `inspectCase`310–323 already validate the full active own family, physical entry digests and advisory-index equality around async reads. A missing/corrupt/mismatched index is an explicit recovery state. Use the existing `reconcileAdmissionsActionsIndex`329–343 only after user review of the exact expected raw index; never reset or fabricate an empty index to permit retirement.
2. **Explicit candidates.** List local status and UUID/kind/revision/reference details. Only entries with descriptor status acknowledged, null pending_state, valid matching ACK ref and exact physical UUID/body digest can be selected. All four pending states remain ineligible. None of this replaces the editor's newer draft or server current.
3. **Prepare.** Capture the full local read, selected raws and exact descriptor/index/fence observations. Fetch and verify the selected native event receipts. After every await, independently verify native owner plus active case/epoch/family generation/tombstone; re-read selected full raw entries and the index, not merely their UUID/header. If the selection became stale, refuse without mutation and require a new choice/verification.
4. **Confirm and recheck.** Immediately before the first removal, rescan the active family and compare selected full raws, acknowledgment refs/status, entry_revision and draft_generation. Confirm the current index remains well-formed and describes the current physical entries. An unrelated newly inserted valid pending entry may be included in a fresh index observation before any mutation; it cannot be silently dropped. If the operation's captured selection or proof became stale, refuse.
5. **Entry first, index last.** For each selected acknowledged key, use existing active/readback primitives; compare its exact raw again immediately before conditional remove, then confirm absence under the same live owner/case/epoch/generation. Do not remove the fence or tombstone. Capture observed progress before attempting the next key. Do not scan arbitrary prefixes or accept unknown/foreign/malformed bytes as deletable.
6. **Merge physical survivors.** Build the next index from a fresh validated physical scan of **all surviving entries**, not `oldIndex.filter(selected)` alone. Keep every sibling/new pending descriptor and its original body. Compare the latest observed valid index raw before replacement and read back the final index/family; use existing scan/index canonical ordering/caps. If its raw changes during the operation, do not overwrite it with an old snapshot.
7. **Honest partial outcome.** Entry removal followed by an index/storage/fence failure can leave stale descriptors or an orphan index. Return partial/residual_unknown with only absence observations actually verified; do not roll back by resurrecting retired intents, remove more keys, silently reconcile, or POST anything. Preserve surviving raw entries and offer explicit index reconciliation followed by a new read. When owner changes, withhold the old private result entirely.

LocalStorage multi-key checks are **not an atomic compare-and-swap**. Cooperating helper writes never turn an acknowledged UUID back into pending: mark-state accepts pending only, ACK replay is read-only, and journal refuses an existing UUID. Sibling insertion/index races are handled by physical-body preservation and final mismatch/residual reporting. Arbitrary noncooperating raw mutation in the final read/remove window cannot be certified absent by this helper; do not claim complete erasure or a transactional snapshot. Observed changed/corrupt raw bytes refuse removal. A family DELETE tombstone or changed generation always wins; retention never removes/replaces it or reopens the family.

The next65th request remains an explicit save operation: review current CAS/source token/body, generate its new UUID, successfully journal → successfully mark sending → one existing native POST. Capacity cleanup itself never dispatches or refreshes a conflicted/pending original UUID/body. If a sibling fills the freed slot first, the next journal still returns limit; keep the draft and require another deliberate choice. A409 original stays conflict and requires explicit reviewed new intent; no auto-bump of CAS/preview.
