## Findings before a G2 source write-ahead

### F1 · High — case-only deletion coordination misses account deletion

The design correctly identifies a PostgreSQL parent→child G2 lock versus child→parent ORM case-deletion cycle (§5, lines 91–103) and proposes locking the parent at the start of `delete_profile`. The **account deletion route is another writer of the same case subtree**. `delete_account` commits its audit event at `routes_account.py:399–412`, then marks `user` deleted, enumerates every profile in sole-owner workspaces, marks each profile deleted, marks organizations deleted, and commits (`:414–429`). `User` has ORM delete-orphan children (`models/auth.py:36–67`); `ApplicantProfileRow` has ORM delete-orphan runs, attempts and schedule (`models/applicant.py:38–52`). Neither account route nor its final delete phase takes a case parent lock before children. SQLAlchemy may emit/hold child locks during its cascade/flush before the profile DELETE. A G2 writer holding profile `FOR UPDATE` then waiting for a legacy/G2 child can therefore cycle with account deletion just as with `delete_profile`. A database-selected deadlock victim could be the native account deletion request, breaking its existing 204/privacy path. The design's sentence that bulk-parent writers need later inspection is accurate, but **case deletion alone is insufficient for concurrent deletion qualification**.

**Minimal finite coordination boundary:** add `routes_account.py` to the G2 adoption allowlist **only for the final deletion transaction**. Preserve password/`confirm_delete_data` checks, the current audit-before-delete sequence, sole-owner/shared-workspace distinction, 204, cookie clear and existing cascades. After the existing audit commit and before `session.delete(user)`, profile enumeration with pending deletes, or any child cascade, start a fresh final-delete transaction and acquire locks in one stable order: affected own organization parent(s), then every affected `ApplicantProfileRow` parent sorted by exact ID, then existing ORM user/profile/organization deletion and final commit. On PostgreSQL use real row `FOR UPDATE`; do not rely on a plain pre-count or identity-map instance. Keep those locks until the final commit. Re-read sole-owner memberships and the affected profile set under this boundary; if they changed, abort safely/reconcile the confirmation rather than deleting a newly shared workspace or silently omitting a new case. The already committed audit must then be reconciled explicitly; a stale `account_deleted` event is not a successful deletion. On SQLite obtain a fresh `BEGIN IMMEDIATE` before any final-delete read or pending ORM deletion; its one-writer reservation is the matching coordination mechanism, not ignored `FOR UPDATE`. No extra profile DML or legacy row is needed.

If that companion account route is not adopted, explicitly label G2 **not qualified for concurrent account deletion**, even if the legacy CAS and single-case delete controls pass. Do not treat a deadlock retry, generic 500, or an account-deletion skip as acceptable privacy proof.

### F2 · Medium — the case-delete companion needs an explicit fresh transaction start

`delete_profile` currently calls plain `owned_profile`, reads run IDs, calls `session.delete(row)`, writes a generic audit event and commits (`routes_profile.py:404–427`). A PostgreSQL parent `FOR UPDATE` must precede run/child cascade work and be reselected with exact ID+organization, preserving native generic 404. A lock call **after** child enumeration/deletion marking is too late to establish the proposed order. On SQLite, `owned_profile` and the run-ID SELECT can already open a read transaction. Starting `BEGIN IMMEDIATE` afterwards is not a safe upgrade if another writer intervened; C10 in the design acknowledges a busy-snapshot risk. The normal dependency Session is also shared with authentication (`security.py:191–239`), whose reads and occasional commits mean `session.in_transaction()` is not an adequate fence test.

**Narrow repair:** specify for this companion route the same clean-boundary rule as G2: retain the frozen principal and route ID, reject unexpected pending ORM state, roll back only a clean read-only auth transaction, then start PostgreSQL's owned parent-lock command or SQLite `BEGIN IMMEDIATE` **before** owner/run/child reads. Recheck owner inside it; do not roll back uncommitted auth changes. Preserve 204, audit detail (`runs_removed`), generic 404 and sibling isolation. The actual session/dialect behavior must be demonstrated with authenticated requests and two physical connections; no nested `BEGIN`, read-snapshot reuse or unhandled busy/500.

### F3 · Medium — the account audit commit is a separate, nonlocking boundary

`routes_account.py:399–412` commits `account_deleted` before the final user/profile/organization deletion. That commit releases any locks and fixes `profiles_removed` from a prior count. A fresh final-delete lock/recheck can detect a membership or profile-set change, but aborting at that point can leave an audit event describing a deletion that did not occur. Conversely, using the old pre-count without recheck can delete a now-shared workspace or miss a new case. This is a bounded design decision required alongside F1, not permission to silently alter the account endpoint's audit/security flow. The `AuditEvent.organization_id` FK itself is `ON DELETE CASCADE` (`models/research.py:209–224`), so the existing sequential test's expectation that one audit row survives (`test_account_flows.py:630–656`) must not be assumed to prove identical PostgreSQL/SQLite retention.

**Narrow choice for root before source:** retain the two-phase audit boundary only with an explicit reconciliation state/event if final deletion aborts, or separately review an atomic audit/deletion policy that can preserve the intended audit semantics across organization deletion. The G2 CAS source stage must not claim a durable account-deletion audit from the new locks alone. This does not reopen any stopped security workflow.

## What the proposed G2 fence gets right

- The native v1/v2 calendar shares one positive child revision and CAS row (`routes_preparation.py:116–163,343–423`; `models/study_schedule.py:16–29`). A strong profile `FOR UPDATE` plus a fresh locked child read can order both present-row updates and first-child inserts through PostgreSQL's immediate FK key-share check, **if** the physical FK/isolation/block relationship is verified as proposed. `FOR NO KEY UPDATE`, a nonexistent child lock or an advisory lock used only by G2 is insufficient for the absent row.
- The clean preflight allows owner-first accepted-UUID replay before mutable access/source/revision gates, then closes its read transaction and rechecks owner/UUID under the fence. This fits native `get_session`/auth autobegin (`db.py:169–175`, `security.py:191–239`) and preserves an original receipt after expiry. The proposal correctly rejects silently committing or discarding a dirty Session. Actual auth-abort and last-seen controls remain necessary.
- SQLite `BEGIN IMMEDIATE` as the first guarded command SQL covers absent and present child writes without changing legacy rows. Busy or unknown-commit outcomes require full rollback and own-UUID reconciliation; a prior read snapshot cannot be reused. The design correctly distinguishes a blocked legacy writer that commits **after** G2 from a revision change committed **before** G2 acquired its fence.
- G2's parent lock is a transaction coordination device, not an authorization, profile timestamp update, second calendar, source-validity proof or global writer lock. Existing generic 404, preparation/research access separation, immutable reference-only receipt and technical-versus-structural legacy revisions remain required.

## Additional finite controls to add to C10/C9 (all NOT_RUN)

1. **Account deletion, G2 wins:** native authenticated G2 holds a profile parent lock; native account deletion with correct password and `confirm_delete_data=true` must wait before child deletion, then erase user, sole-owner org, all profiles/G2 rows/legacy/attempts and return 204. Cookie is cleared, later auth is 401, and an accepted G2 UUID cannot replay after deletion. Record the actual audit outcome under both enforced-FK dialects; do not infer it from the SQLite-only sequential expectation.
2. **Account deletion wins:** account route acquires its ordered final-delete boundary first; G2 waits then returns generic owner 404 with no new current/history row or resurrected case. A different user's shared organization/case survives exactly.
3. **Refusal and scope:** wrong password stays 400; missing `confirm_delete_data` with cases stays 409 and deletes nothing; a shared workspace survives member departure. A membership/profile-set change across the audit commit/final-delete boundary yields safe revalidation, not deletion based only on the stale pre-count. Existing `test_account_flows.py:630–687` covers sequential semantics but is not a concurrency proof.
4. **Both dialects and auth state:** use real migrated SQLite/PG, separate connections and native routes. Verify PostgreSQL lock order and no deadlock; verify SQLite immediate start after auth/audit transaction with FK/busy pragmas, bounded contention outcome, and no nested-BEGIN/read-upgrade failure. Failed deletion or G2 transaction is fully rolled back and does not report 204/ACK falsely.
