## Finding requiring source-proposal alignment

**F1 — navigation policy differs between accepted write-ahead and design prose.** Design §4 says a leave warning is mandatory only for failed persistence and permits navigation after a successful journal write with a status label. Root write-ahead resolution instead requires guarding **all meaningful unsaved draft or unresolved pending** navigation, case switch and hash changes. A persisted journal makes recovery possible but is still not a server save or acceptance. The source packet should implement the explicit root write-ahead policy, with Cancel before the first App screen/hash/case mutation and no alert for an accepted ACK with no later edits. Any decision to relax the guard needs an explicit root design resolution before applying source.

## Confirmed boundaries and finite source review checks

- `auth:${draftIdentity(principal)}` matches native `currentApplicantOwner()`'s `auth:${JSON.stringify([user_id, organization_id])}`; the proposed `ashyq.owner.` session key is covered by existing owner-change/logout data cleanup. Recovery must refuse the null identity and anonymous fallback. A separate demo tree is allowed only after explicit auth-disabled binding. An old A tree must check its captured owner before every storage read/write/remove after a B binding.
- A pending body must be stored **before** a new PUT. If the initial session write fails, retain the exact UUID/body in memory as `not_sent` and do not dispatch; after a PUT has gone out, any failed state update cannot erase the durable original `sending` body. Reload maps that body to `uncertain`, does no automatic PUT/preview, and offers only an explicit exact-body retry.
- A current GET reconciles only after strict own profile/view/receipt matching. If the validated current revision is greater than `original.expected_revision + 1`, exactly one owned history GET for that target revision is sufficient; any accepted original CAS write must occupy that revision. A mismatching/missing history receipt leaves pending intact. A late ACK clears only the matching owner/case/draft ID/full original body and preserves edits made after submission; older ACK U cannot remove newer pending V.
- Public legal remains accessible when `!status?.authenticated`, including unknown status with no private child tree. Authenticated legal should pass through the existing keyed App `LegalScreen`, so its navigation guard can act. The mandatory storage-owner event still immediately unmounts the private tree and is not delayed by a dialog; it is distinct from voluntary navigation.
- Successful case delete ACK should remove only the exact captured owner/case journal, even if B became active while A deletion awaited. Failed delete and ordinary save ACK have different cleanup rules. Existing logout/account-delete owner-scoped cleanup stays authoritative. Storage failure after server ACK must not fabricate a failed server deletion.
- Typed restore should preserve the raw canonical write body, optional-field omission, input order, exact refs and bounded personal fields. It must reject malformed/foreign/oversized records before paint or dispatch, without enriching premium source data. A journal is no authority for access, source currency, content availability or admission outcomes.

The design header's statement that full terminal evidence is unqualified is historical context; root has since sealed the G2 full local receipt. It should not be repeated as current release status in the source packet. These are source-proposal review criteria, not implementation PASS.
