## Concrete design gaps before a source proposal

1. **F1 — import's source fence needs a transaction boundary with the native profile writer.** The plan says a changed/reordered `activities` or `achievements` array invalidates an in-flight import (`plan:16,32`). Native profile `PUT` replaces the whole JSON payload and commits without a revision/CAS (`routes_profile.py:104–126`). A preview fingerprint alone cannot guarantee this rule during a concurrent profile update. For a new import command, re-read the exact owned source arrays and compare the preview fingerprint/index/semantic digest **inside the same guarded transaction** as the portfolio current+event insert; on PostgreSQL lock the profile row before reading, and on SQLite use the established write reservation before reading. An import that loses this race returns a typed conflict and creates no item/event. Same UUID replay must check its accepted command before fresh mutable-source comparison, as the plan already states. This is a finite new-command coordination requirement, not a request to rewrite legacy profile `PUT` or infer an individual-user owner beyond the existing organization/case authority.

2. **F2 — an imported source observation must be stored, not just locatable by index.** The plan requires showing the imported source observation separately from later personal edits (`plan:16–17`) and exporting origin references/history (`:20`), but lists only a source fingerprint, array kind/index and semantic digest. Those identifiers cannot reconstruct the exact chosen Activity/Achievement after a profile reorder or edit. The accepted import event should retain a bounded private snapshot of the selected typed source record (or an equivalent exact versioned representation), its kind/index/fingerprint/digest and acceptance time. Current portfolio fields may then diverge while history and owner export still show the original applicant-reported input. No automatic write-back to `ApplicantProfileIn` follows from that snapshot.

3. **F3 — legacy evidence strings need an explicit import decision.** Native `Activity.evidence_links` and `Achievement.evidence_links` are bounded `Str200` arrays (`profile.py:189–216`); the profile schema does not require absolute public HTTP(S) URLs. The new plan allows only bounded public HTTP(S) evidence destinations without credentials/private tokens (`plan:19`). An explicit import may therefore encounter a valid profile record containing a link that is invalid for the new portfolio. Preserve the exact source observation privately, reject or omit the unsafe *actionable portfolio link* with a visible reason, and never fetch, silently convert or mark it verified. Choose the exact behavior in the future import DTO/acceptance contract before implementation.

## Source alignment and limits

- `ApplicantProfileIn` has up to 30 Activities and 30 Achievements, without stable per-item IDs (`profile.py:189–216,331–341`). Stable portfolio IDs and distinct records with equal names are appropriate. `Activity` contains optional duration/workload/outcome, but no start/end date; `Achievement` has year/placement/criterion. Imported records must leave unsupported dates and measured outcomes absent instead of deriving them from role, title or `Activity.annual_hours` (`profile.py:203–207`). A `project` kind has no separate native source shape and should enter as an applicant-entered record unless a later explicit mapping is approved.
- The plan's case boundary matches `owned_profile`'s organization-scoped 404 behavior (`tenancy.py:12–24`), while the wording “applicant-owned” must retain that actual shared-organization authority. New rows need case FK/ORM cascade independent of SQLite FK settings, following `ApplicantProfileRow`'s documented pattern (`models/applicant.py:24–52`). Own export must extend the current “complete record” endpoint with current portfolio and accepted history (`routes_profile.py:268–280,317–401`); case deletion must remove both without touching sibling cases. Reading accepted own history after subscription expiry and deletion remain explicit in the plan. Its policy for **new** portfolio creates/edits after expiry is not yet specified; decide it separately from paid learning access rather than borrowing that gate implicitly.
- The plan correctly separates applicant-reported facts from verified achievements and official requirements; no profile, official test, result/check, ranking or admission probability is silently updated (`plan:9,13–22`). Its no-public-social, no-attachments, no-portal-credentials, no URL-fetching and no AI-writing/ranking scope is coherent. Evidence links prove neither truth nor authorization. Current/history UUID+digest/CAS and owner/case/intent fences are stated as future controls, not verified behavior (`plan:18,28–35`).

**Disposition:** suitable as a bounded future direction after F1–F3 are made explicit in the next typed/persistence design. It is not an integrated private portfolio, export/delete proof, deployment, scored admissions advice or production acceptance.
