# In-memory strict-confirmed routing retention — external proof contract

OFF remains the native flow. ON complete results, cap membership and ordinary claims are unchanged. No new stop/cut, no extra source budget, no selection ranking, no programme/fact applicability rule, no durable observation namespace.

At an actual successful native confirmation (confirmation loop or catalogue `_read_lead`), a synchronous callback may inspect the already-read result. It publishes only a strict own-H1/title/whole-known-field + local offered-degree + unchanged scoped academic-content routing token. Legacy `profile_rejects` acceptance alone is insufficient: Data Science, split/reversed/related fields, department-only and funding pages publish nothing. Explicit non-degree/visiting degree-denial purpose must abstain; it is not a target full degree. Year/intake/campus/population remain UNKNOWN even for a published token.

The callback does not mutate the native selected list or completed trace. It makes a bounded provisional candidate/trace snapshot during NORMAL confirmation, before the next await. CandidateProgram is a routing lead, never a verified ProgrammeResult/Claim. The normal `_apply` mapping may run only there on copies; never in exception/finally. Native confirmed order and existing three-slot cap decide eligibility; a fourth strict source cannot retroactively enter the partial candidate if normal completion would have omitted it. Strict subset may be incomplete for multi-field requests; no coverage completion is inferred.

Publish the exact snapshot to the owning wrapper before optional work. Catalogue decoration retains catalogue id/source and upstream identity diagnostics. When a real typed `UniversityReadStopped('read_cap')` reaches the wrapper, it can return that already-published routing snapshot with an explicit partial/unknown limitation. Cumulative native query attempt counters must be refreshed from the still-current trace, without replacing routing/scope facts or refunding later attempts. No `_apply` on unwind, Fetcher call, callback SQL, Claim or budget reset.

Whitelist is only `read_cap` in this prototype. Production currently has no typed deadline emitter. Actual `TimeoutError`, harness source-work deadline and `asyncio.CancelledError` must keep original propagation, not be relabelled into native read-cap success. Callback memory is not durable and the runner assigns `_candidates` only after `adapter.discover` returns. Therefore current asynchronously-cancelled Groningen remains NOT FIXED and cannot be claimed as quality gain.

`checkpoint_busy`, cancellation, lease loss, invalid/unfenced episode metadata, arbitrary typed reason and provider refusal cannot be returned as partial routing success. Provider seam currently catches SearchError and reports many refused queries rather than retaining original exceptions. That is a real existing propagation boundary: direct mocked method raises are not proof of genuine native provider refusal behavior. Preserve a RED if the actual provider path cannot meet the requested propagation contract without broader changes. No provider/Worker policy expansion is silently bundled.

Runner/Worker proof must use genuine enqueue/claim token1, actual Worker.execute/_dispatch/run_to_decision and existing native BudgetedFetcher reserve-before-get SQL in own isolated SQLite. Only source transports/generators are synthetic. Observe durable native count60 before every original transport call; the next read refuses before I/O. A retained URL can be exposed to the runner while requirements/funding remain unknown and ClaimRow stays0. Existing normal lifecycle may mark the transport Job succeeded after completing an explicitly unknown pipeline; record that actual status, never describe it as verified programme or complete source research. Stage counters `programmes checked` count attempts, not new claims.

Successful later runner `_save` uses a genuine attempt/worker/status heartbeat fence and commits; callback itself guarantees no durable ack. SourcePage metadata `record/flush` is earlier, not atomic durable confirmed evidence. Busy/lease/cancel paths must preserve original native behavior; no new SQL/claims from the callback. Existing cancellation/failure handlers may make their original status writes: that is not a zero-SQL guarantee for the whole Worker. Crash/restart/cancel durability requires the separate broader contract already sealed. SQLite does not prove PostgreSQL contention behavior.
