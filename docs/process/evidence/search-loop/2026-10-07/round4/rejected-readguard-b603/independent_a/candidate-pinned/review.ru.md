**Порядок сохранения и пределы блокировок.** До original get helper читает fresh durable snapshot, reserves count, вызывает существующий `_save` с conditional heartbeat по job/run/status/worker/attempt, и допускает I/O только после commit. Failed commit или final heartbeat refusal откатывает reservation и не допускает `_get`. `RunCancelled`, `LeaseLost` и внешний `CancelledError` сохраняют отдельные control semantics; broad sitemap/walker/renderer catches их не переименовывают.

На PostgreSQL новые locking SELECTs запрашивают **Job→Run, оба FOR UPDATE NOWAIT**. Это выбранное решение после обнаружения противоположного порядка у cancel/recovery writers. 55P03 превращается в `checkpoint_busy` unknown с rollback и нулём I/O. Guarded cancellation reads выполняются без autoflush: pending progress не должен незаметно записать Run до Job lock. Проверка реальных SQL statements подтверждает этот порядок для dirty progress. Это не доказательство, что вся transaction никогда не удерживает другие row/table locks: более ранние ORM flushes, `SourcePage`/result persistence и сторонние writer paths требуют отдельного PostgreSQL review. Общую deadlock freedom и bounded DB latency не заявляем.

SQLite игнорирует `FOR UPDATE`. Последний независимый двухсессионный контроль подтвердил существенный дефект predecessor: **два actual get тела, сохранённый count=1**. Исходник и raw red сохранены в `rejected-no-sqlite-write-lock`, а не заменены успешным результатом. Окончательный вариант делает no-op conditional UPDATE owned Job на SQLite до чтения Run snapshot; он приобретает настоящую write transaction, не меняя lease/state values. Original `_save` по-прежнему выполняет heartbeat и commit. BUSY/LOCKED дают `checkpoint_busy` unknown. Реальные SQLite-контроли подтверждают два get→count2, два sessions/один attempt/80 попыток→60 admission и настоящий BEGIN IMMEDIATE lock refusal→0 I/O. Это threaded local SQLite verification; отдельный cross-process crash test не выполнялся.

После write lock прежний fixture пытался изменить locked Job из другой session между reservation и commit и закономерно получил database locked. Этот failure сохранён. Fixture разделён на actual takeover **до Job lock** и отдельный final heartbeat-refusal rollback. Guard не ослаблен ради прохождения теста.
