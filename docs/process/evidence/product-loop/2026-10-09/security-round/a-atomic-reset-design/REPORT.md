# Atomic password-reset follow-on — DESIGN_ONLY

Current source: `backend/app/api/routes_account.py:233–252` reads a reset row, checks `used_at`, then mutates the password and `used_at` in separate ORM assignments. Two genuine transactions can both pass the read predicate. This is a source-confirmed missing atomic claim; concurrent PG exploitation has NOT been executed. Existing sequential single-use test496–511 is useful but cannot prove concurrent single-use.

Small cross-dialect repair: preserve the initial validity/user/workspace checks and password validation, calculate the password hash into a local scalar without assigning it, then claim the exact token using one conditional UPDATE: matching token ID/hash, `used_at IS NULL`, `expires_at >= captured_now`, set `used_at=captured_now`. Require actual rowcount exactly1; zero means the unchanged generic400 plus rollback. Only the winning transaction may then assign User.password_hash, revoke sessions and add reset-completed audit. Do not use SELECT FOR UPDATE alone: SQLite ignores that lock. Do not assign password before the conditional UPDATE, including environments where ORM autoflush is enabled. The existing production SessionLocal disables autoflush (`db.py:53`); tests can use different defaults, so ordering must be explicit.

PG READ COMMITTED evaluates the conditional UPDATE after a conflicting writer finishes; SQLite serializes writers. The design requires real dialect tests, not SQL compilation. Actual SQLite settings declare WAL/busy_timeout15000ms (`db.py:37–49`); a held read snapshot may still produce BUSY/SQLITE_BUSY_SNAPSHOT. Preserve/rollback that error honestly, never report reset success or issue a cookie; do not add unlimited retries. Future finite test must distinguish normal serialization from explicit lock refusal.

Native commit boundary matters: reset route commits token/password/revocations/audit at272, then `security.create_session:151–177` commits a new session at164 before setting the cookie. CAS makes at most one request reach that helper; it does NOT make the two commits crash-atomic. A process failure between commits may consume the token without a new session. If the future acceptance requires token/password/new-session atomicity too, that is a separate explicit helper change (stage session, commit once, then cookie), not a claim supplied by this minimal CAS design.

Minimum meaningful future regression: two independent real sessions/connections and two native route invocations use the same synthetic valid token and different valid passwords. A barrier proves both have passed the initial unused-token read (no replacement of the SQL claim/password/session methods); release into the actual conditional UPDATE. With normal lock completion, exactlyone response200/new cookie, exactlyone loser400, token used, exactlyone reset-completed audit, one post-reset AuthSession, old sessions revoked, winner password verifies and loser password does not. Record actual SQLSTATE/SQLite error code and transaction/connection identities; run independently on owned SQLite and isolated local PG. Validate the helper's real commit, not a fake invocation counter. A second failure-injection boundary must rollback a claimed token on precommit error and produce no cookie; queued, not currently run.

Existing expired/inactive/no-workspace/disabled-recovery/second-use assertions stay intact. Password recovery is false in supplied fly.toml declarations; actual deployed config unknown. No verification-flow invention, provider calls or primary changes. This is queued design, not a fix or launch acceptance.
