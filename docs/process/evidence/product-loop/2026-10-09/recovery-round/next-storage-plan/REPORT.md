## Proposed minimal general seam (not a current contract)

Backend: add a separate per-user mark model (registered in models metadata), a deterministic checklist inventory/revision helper, and sidecar result GET/update beside existing result routes. Foreign authority derives from native principal+owned result; no body-supplied user/organization/case override. Storage uniqueness is personal user + result + checklist revision + item reference; case/run membership is verified through the current result chain. Worker evidence payloads, Claim status, choices/notes and current responses remain untouched.

Revision recommendation: explicit helper-version namespace plus canonical full serialized checklist, omitting only generated_at, with authoritative result/programme identity. Arrays, scope, source references, required/format/purpose/owner/deadline/prompt/dependencies/unresolved/completeness remain included. Never use requested-year defaults, title matching, row.updated_at or generated_at as version. Any changed non-timestamp content invalidates current marks conservatively; no cross-run/name/fuzzy transfer. This may reset marks on claim-ID/order/diagnostic changes even when a person considers the task similar; that is an honest first-version limitation.

Inventory covers the existing four rendered actor-action arrays, not a second duplicate inventory from admission/scholarship arrays. Within a revision, refs distinguish array path and original source occurrence, including duplicate names. Attach refs before UI lead-time sorting; sorted indices are not stable refs. Sidecar may carry inventory references without changing evidence item schemas.

Update one ref by absolute done true/false with expected checklist revision and per-mark write version. Verify current revision/membership and save atomically with the authoritative current result; stale worker rebuild or old write returns explicit conflict. Replaying an absolute set never toggles a mark; a stale replay may require reread instead of being falsely called saved. Different items must not overwrite an entire map. Transaction/lock strategy requires real native SQLite/PostgreSQL tests and existing worker lock-order audit, not a claimed guarantee from this plan.

Frontend: use native cookie client, principal+organization/case/run/result/revision view key and generation guard. No durable local fallback that impersonates server save. Old unscoped docsDone ticks are not automatically assigned to an account. On identity/case/version change clear prior personal view, ignore late responses, reload progress; show pending/saved/unsaved-error/conflict explicitly. Existing saved choices and checklist evidence remain.

Privacy: result/case/user erasure must remove personal marks through native ORM/FK erase behaviour; case export must include only the requesting principal's marks, not other workspace members' personal marks. Current export/erase boundaries need intentional extension, not a new account-deletion API. [profile export/delete](/Users/wpalish/Documents/Codex/2026-10-07/x20/work/ashyq-apply/backend/app/api/routes_profile.py:266), [User model](/Users/wpalish/Documents/Codex/2026-10-07/x20/work/ashyq-apply/backend/app/models/auth.py:32).
