# ASHYQ: правила команды агентов

## Что это

Этот регламент и `crew.json` — инструкции координации для главного агента, не встроенный scheduler ZCode и не системная sandbox. Нативные определения subagents находятся в пользовательском `~/.zcode/agents/`. Изоляция контекста subagent не означает отдельную файловую систему.

Работаем только над ASHYQ Apply. Сначала прочитай текущие инструкции репозитория. Не заменяй их этим документом. Если `ai-team/crew.json` отсутствует или полученная задача относится к другому проекту, остановись и сообщи о несоответствии.

## Не менее четырёх независимых участников на задачу

Для КАЖДОЙ задачи обязательны реальные отдельные вызовы:

1. `ashyq-planner` — спецификация, root cause, контракт и scope.
2. `ashyq-qa` — независимые регрессионные проверки и подтверждение результата.
3. `ashyq-developer` — реализация.
4. `ashyq-reviewer` — независимый review итогового candidate SHA.

На security/money/concurrency/data-loss задачах дополнительно нужен `ashyq-security`. `ashyq-integrator` проверяет готовность объединения; это отдельная роль, она не заменяет четыре обязательных роли.

Одна модель GLM для всех ролей допустима. Но один ответ с четырьмя заголовками — НЕ четыре агента. Не выдумывай invocation IDs, результаты tools и логи. Сохраняй реальные ссылки/идентификаторы вызовов, видимые в runtime. Если их нельзя подтвердить, отметь независимость как непроверенную.

Только главный агент вызывает subagents. В текущем ZCode subagents не могут создавать собственных subagents. «Команда задачи» — логическая группа вызовов главного агента, не вложенное дерево агентов.

## Власть и права

- Главный агент: единственный владелец общей очереди, назначений, ресурсных резервов и task ledger. Не пишет исправления production-кода сам.
- Planner/reviewer/security: read-only инструменты; результат возвращают главному агенту. Они не меняют код ради прохождения проверки.
- Developer: меняет только согласованный production scope в своей task worktree. Не ослабляет QA assertions.
- QA: пишет тесты в собственной worktree. Не исправляет production-код и не подгоняет ожидаемое поведение под текущий баг.
- Integrator: работает только в выделенной integration worktree, когда активен единственный integration slot. Не решает смысловые конфликты произвольно.
- Пользователь: разрешает push, merge в защищённый main, deployment и операции с реальными данными. По умолчанию всё это запрещено.

Наличие Bash позволяет технически менять файлы; текстовый scope — не OS sandbox. Для недоверенного кода и жёсткой изоляции нужны отдельные контейнеры/пользователи. В данном комплекте нарушение scope выявляется при проверке diff и блокирует принятие результата, а не гарантированно предотвращается на уровне ОС.

## Изоляция worktrees и single-writer

Никогда не запускай двух пишущих агентов в одном checkout. Для каждой задачи создавай собственные ветки/worktrees на фиксированном baseline SHA. Предпочтительная последовательность:

1. Planner фиксирует contract; QA исследует сценарий на том же baseline.
2. QA создаёт regression tests на ветке `ai/<campaign>/<task>/qa`, запускает их на baseline и фиксирует RED или уже исправленное поведение.
3. Developer получает новую ветку/worktree от QA commit и реализует исправление. QA больше не изменяет этот commit.
4. Новый вызов QA проверяет candidate SHA в отдельной verification worktree. При обнаружении новых тестов сначала фиксируется изменение тестового контракта, затем новый candidate.
5. Reviewer и security reviewer могут параллельно читать ОДИН замороженный candidate SHA. Нельзя менять его в процессе review.
6. Integrator собирает принятый candidate с текущей integration branch и повторяет affected gates. Изменившийся код требует повторного review.

Planner, QA и reviewer могут исследовать параллельно. Параллельность на одной задаче не означает, что все должны одновременно редактировать production-код. Быстрее масштабировать независимые задачи, чем конкурирующих редакторов одного файла.

Не используй `git worktree add --force`, чтобы открыть одну branch дважды. Не копируй production `.env` в worktrees. Тестовые DB, ports, caches и output должны быть раздельными; shared dependency cache допустим только при безопасном использовании.

## Резервы ресурсов и область изменений

Главный агент до начала письма резервирует `locks` и `allowed_paths` из task card. Запрещено параллельно выполнять задачи с общим резервом или пересекающейся областью записи.

Резервы — координационная дисциплина единственного диспетчера, НЕ нативные файловые блокировки ZCode. Не запускать второй независимый главный агент на той же очереди. Для автоматических жёстких блокировок нужен отдельный исполняемый orchestrator; этот комплект его не изображает.

Перед каждым запуском сравни реальные файлы, а не только названия locks. Если нужен дополнительный файл:

- остановить запись вне scope;
- запросить расширение у главного агента;
- повторно проверить пересечения и зависимости;
- обновить contract и только затем продолжить.

Особо сериализуются:

- `backend/app/schemas/**`, `frontend/src/types.ts`, API contracts;
- Alembic migrations и цепочка heads;
- `backend/app/pipeline/runner.py`;
- `frontend/src/lib/store.tsx`;
- shared tests (`test_api.py`, `test_pipeline.py`, общие fixtures);
- dependency lockfiles;
- CI/config/deployment;
- общий PostgreSQL test cluster;
- default/auth E2E с общими портами;
- integration branch.

Worktrees защищают от случайных совместных правок checkout, но не устраняют смысловые конфликты при merge. Чистый Git merge ещё не означает совместимость.

## Передаваемый task packet

Каждый вызов получает пакет по `templates/TASK_PACKET.md`:

- task ID, finding IDs, attempt ID;
- role, реальная ссылка на invocation, если runtime её предоставляет;
- абсолютный workspace/worktree path;
- полный baseline/candidate SHA;
- цель, acceptance и non-goals;
- разрешённые файлы, зарезервированные ресурсы;
- замороженный contract;
- входные artifacts и ожидаемый результат;
- ограничения сети/секретов/опасных операций.

Не предполагай, что subagent видит память главного чата. Передай необходимое явно. `AGENTS.md` и общий регламент subagent обязан прочитать; не полагайся только на автоматическую инъекцию в старой версии ZCode.

## Статусы и критерии

`BACKLOG → READY → PLANNED → TESTS_READY → IMPLEMENTING → VERIFYING → REVIEWING → INTEGRATION_CHECK → DONE`

Боковые статусы: `BLOCKED`, `CHANGES_REQUESTED`, `ALREADY_FIXED_VERIFIED`.

- `READY`: dependencies завершены, baseline зафиксирован, scope свободен.
- `PLANNED`: planner вернул contract и acceptance.
- `TESTS_READY`: QA показал защищающие сценарий тесты. Для уже исправленного багa допускается обоснованный GREEN на baseline.
- `VERIFYING`: candidate заморожен, developer завершил работу.
- `REVIEWING`: QA gates выполнены на этом candidate.
- `DONE`: четыре независимые роли подтверждены, дополнительные reviews получены, combined integration SHA проверен; локальная интеграция не означает push/deploy.

Любая новая правка после review инвалидирует прежнее разрешение на старый SHA. Если full gate недоступен, задача не становится release-ready только потому, что unit test прошёл.

## Правила исправления

- Сохраняй user changes, approvals, notes и документы.
- Не понижай coverage, не удаляй failing tests, не меняй assertions без причины из требований.
- Не ослабляй auth, CSRF, proxy trust, SSRF, tenant scoping и production scrypt.
- Unknown не равен нулю; возможность scholarship не равна гарантированным деньгам.
- Не создавай новые архитектурные компоненты без необходимости.
- No push/deploy/production migrations/secrets extraction без разрешения.
- Не запускай нагрузочные или security probes против чужого/публичного сервиса.
- Не обещай, что ошибки полностью исключены: сообщай конкретные проверки и их ограничения.

## Backpressure вместо бесконечных повторов

`crew.json` содержит предлагаемые профили параллелизма, не настройку native runtime. Реальный предел может быть ниже из-за ZCode, API, памяти и файловых зависимостей.

При 429/5xx используй bounded backoff и снижай параллелизм; при OOM/нестабильных tests — сериализуй тяжёлую работу. Не обходи rate limits и не переключайся на платный API молча. После двух одинаковых неуспешных repair loops верни planner/root-cause analysis, после повторного отсутствия прогресса — BLOCKED с доказательствами.

Не давай модели самой принять собственный код за проверенный. Однородная команда GLM сохраняет общие blind spots; нужны независимые тесты, проверка исходников и human gate на опасные решения.
