# ASHYQ Apply — Поиск вузов 2.0
## Полный технический дизайн: обученная модель + всегда свежие данные, без галлюцинаций

**Куда встраивается:** существующий пайплайн `discovery → classification → extraction → verification → freshness`
**Что заменяет:** regex-экстракцию как единственный путь; ручной реестр из 19 вузов; per-worker дисковый кэш
**Чего НЕ меняет:** контракт `Claim` (URL + дословная цитата + дата + специфичность) — это фундамент, модель работает *под* ним, а не вместо него.

# 0. Диагноз: почему сейчас recall 1/10

Прежде чем что-то «обучать», надо точно понимать, где именно рвётся цепочка. По их же аудиту (`docs/LIVE_DISCOVERY_REPORT.md`) и коду:

| Этап | Что происходит | Где рвётся |
|---|---|---|
| **Discovery** | sitemap-first, лимит 40 URL на категорию, 3 страницы на категорию | Категорию (admissions/costs/scholarships) находит в 26/30 случаев — **этот слой почти работает** |
| **Program discovery** | до 8 программных кандидатов, каждый должен пройти `classify_page` как `PROGRAM_DETAIL` | **Вот здесь провал: 1/10.** Программные страницы вузов бывают JS-каталогами, каталогами с фильтрами, страницами без слов «programme» в заголовке — regex-классификатор их не узнаёт |
| **Extraction** | regex + «страница должна принадлежать классу» | Работает на страницах, которые нашлись. Но: 15+ задокументированных FP (отрицания, индексные страницы, год не тот) |
| **Freshness** | окно 30–180 дней на тип claim + ручной recheck | Работает, но recheck перечитывает всё и ломается цепочкой (T13) |

**Ключевой вывод:** главная дыра — не «модель плохая», а **program discovery + экстракция с длинным хвостом форматов**. Поэтому архитектура ниже — четырёхуровневая, где модель добавляется там, где детерминированные слои сдаются, и **никогда не является источником истины**.

# 1. Целевая архитектура — 4 слоя экстракции + 3 контура свежести

```
                        ┌─────────────────────────────────────────────────┐
                        │  ЗНАНИЕ = таблица claims в PostgreSQL            │
                        │  (не страницы, не кэш, не память модели)         │
                        └─────────────────────────────────────────────────┘
                              ▲                              ▲
              запись          │                              │   чтение
   ┌──────────────────────────┴──────────────┐   ┌───────────┴───────────────┐
   │  ВЕРИФИКАТОР (детерминированный)         │   │  Ранжирование/подбор      │
   │  цитата ∈ текст страницы? URL офиц.?     │   │  (существующий scoring)   │
   │  дата? специфичность? формат значения?   │   └───────────────────────────┘
   └────────────▲─────────────────────────────┘
                │ только то, что прошло верификатор
   ┌────────────┴─────────────────────────────────────────────────────────┐
   │  ЭКСТРАКЦИЯ (4 яруса, эскалация по стоимости)                        │
   │  T0: структурированные данные (JSON-LD/schema.org, таблицы, PDF)     │
   │  T1: детерминированные парсеры (текущие regex, исправленные)         │
   │  T2: LLM-промпт (frontier API) — кандидатные claims                  │
   │  T3: дообученная малая модель (self-hosted) — кандидатные claims     │
   └────────────▲─────────────────────────────────────────────────────────┘
                │ страницы
   ┌────────────┴─────────────────────────────────────────────────────────┐
   │  FETCH & CHANGE DETECTION                                             │
   │  robots/politeness (есть) + ETag/Last-Modified + content-hash         │
   │  + sitemap lastmod → инкрементальный обход                            │
   └───────────────────────────────────────────────────────────────────────┘
```

**Главный инвариант (то, что делает систему «безопасной»):**

> Слои T2 и T3 (модели) **не могут создать факт**. Они создают `ClaimCandidate`, который живёт ровно до вызова верификатора. Верификатор — обычный Python без нейросетей — проверяет четыре вещи и отклоняет кандидата при провале любой:
> 1. `excerpt` — **дословная подстрока** текста страницы (после нормализации пробелов);
> 2. `source_url` — принадлежит регистрируемому домену вуза (суффикс-матч, не подстрока!);
> 3. `value` — соответствует формату и диапазону для `claim_type` (IELTS 0–9 с шагом 0.5; год ≥ текущего; сумма > 0 и < 1 млн и т.д.);
> 4. `page_type` — страница прошла классификацию, допускающую этот claim_type.
>
> Галлюцинация модели в этой схеме стоит максимум один отклонённый кандидат и строчку в логе. Она **не может** попасть в таблицу claims.

# 2. Слой Discovery: от 19 вузов к 300 без потери точности

## 2.1 Три источника институций (в порядке приоритета)

**A. Кураторский реестр (расширенный).** Сейчас `institution_registry.json` — 19 записей. Расширить до 100–300 по одному принципу: **вуз попадает в реестр только после того, как канарный прогон подтвердил ≥ 2 из 4 категорий** (admissions / costs / scholarships / program catalog). Структура записи уже подходит; добавить поля:

```json
{
  "homepage": "https://www.rug.nl/",
  "domains": ["rug.nl"],
  "locale_hints": ["en", "nl"],
  "catalog_seed": "https://www.rug.nl/bachelors",        // ручной seed, проверяет человек
  "admissions_seed": "https://www.rug.nl/education/bachelors/admission-requirements",
  "structured_data_expected": true,   // вуз публикует JSON-LD Course?
  "canary_status": "verified_2026_09_05",
  "canary_recall": {"category_pages": "3/4", "program_pages": "12/30"}
}
```

Приоритет заполнения — по статистике выезда казахстанских абитуриентов: 🇵🇱 Польша, 🇨🇿 Чехия, 🇭🇺 Венгрия, 🇩🇪 Германия, 🇳🇱 NL, 🇬🇧 UK (актуально не для всех), 🇰🇷 Корея, 🇹🇷 Турция, 🇰🇿 NU + казахстанские программы бикурикулума, 🇺🇸/🇨🇦 частично. 19 → 60 за первый спринт (по 5–8 вузов в день канарными прогонами) → 150–300 к месяцу.

**B. Программные каталоги вузов — главный новый источник.** Почти каждый крупный вуз имеет *официальный* каталог программ (often `/bachelors`, `/programmes`, `/study`, `/education`), и это **структурированный или полуструктурированный список всех программ с ссылками на детали**. Сейчас discovery идёт через sitemap-категории и находит каталог как «категорию», но **не раскрывает его в список программ**. Новая ступень: `catalog expansion` — страница классифицируется как `PROGRAM_CATALOG` (классификатор уже знает этот тип!) → специальный walker извлекает из неё все ссылки на программы (таблица `<a>` + текст-окружение: название, степень, язык) → каждая попадает в очередь `program_detail` на верификацию. Это напрямую бьёт в recall 1/10: не нужно *угадывать* программную страницу из sitemap — каталог её отдаёт явно.

**C. Структурированные данные (schema.org).** Значительная часть вузов публикует JSON-LD `Course` / `EducitationalOccupationalProgram` / `Offer` (цена!) прямо на программных страницах. Это не источник новых вузов, но источник программ и цен внутри вуза с **нулевым** риском FP. T0-экстракция ниже.

## 2.2 Каталоговый walker (новый модуль `adapters/discovery/catalog_walker.py`)

Алгоритм:
1. Страница классифицирована как `PROGRAM_CATALOG`.
2. Извлечь все `<a href>` с текстом ≥ 10 символов, у которых URL-путь содержит / ведёт на тот же домен.
3. Для каждой ссылки посчитать признаки «программности» по окружающему тексту: слова `BSc|MSc|BA|MA|Bachelor|Master|LLB|LLM`, паттерн «предмет + степень», нахождение в `<table>`/`<li>` повторяющейся структуры.
4. Отсортировать по скору, взять top-N (N = `verify_limit`, сейчас 20; лимит поднять до 50 — см. §7).
5. Каждую ссылку fetch'ить (через существующий `Fetcher` — polite, robots, кэш) → `classify_page` → если `PROGRAM_DETAIL` — это кандидат с URLом; если нет — записать в `page_outcomes` с причиной.
6. **Сопоставление с профилем абитуриента** (уже есть фикс `02d648c` «filter live programmes by profile»): фильтровать по степени (bachelor/master), языку, полю (field match по тексту названия), гражданству, где вуз публикует ограничения.

Критерий приёмки: на 10 канарных вузах — **recall программной страницы ≥ 7/10** (сейчас 1/10). Это главный KPI всего редизайна.

## 2.3 JS-каталоги (Playwright-тир — уже есть, включить для каталогов)

Часть каталогов — клиентский React/Vue со списком из API. Уровни обработки:
1. `Fetcher` уже эскалирует на Playwright при < 400 символов текста — работает.
2. **Новое:** после рендера дождаться сетевого покоя (сейчас есть таймаут — проверить, что он ждёт XHR-списки), и **перехватить JSON-ответы** (`page.on("response")`): каталоги часто тянут JSON с идеальной структурой (name, degree, url, tuition). Если JSON перехвачен и в нём есть массив объектов с `name`+`url` → это программный список **без парсинга HTML вообще**.
3. `fixture://`-механизм репетирует это в demo: добавить 2–3 JS-каталог фикстуры в corpus, чтобы путь был покрыт тестами офлайн.

# 3. Слой экстракции: 4 яруса и правило эскалации

## 3.1 T0 — структурированные данные (бесплатно, детерминированно)

Новый модуль `adapters/extraction_structured.py`:

1. **JSON-LD** (`<script type="application/ld+json">`): типы `Course`, `EducationalOccupationalProgram` → название, степень, провайдер; `Offer` внутри → цена tuition с валютой; `startDate`/`applicationDeadline` → дедлайны. Маппинг в `ClaimType` — таблицей, не кодом.
2. **Microdata/RDFa** — редкость, не делать в первой итерации.
3. **HTML-таблицы стоимости** — у costs-страниц структура `<table>` встречается часто; текущий `web_costs.py` читает текст, добавить чтение таблиц по заголовкам колонок («Tuition», «Non-EU», год).
4. **PDF** — уже есть (pypdf); у dos. фиксированные таблицы фи (u-groningen fees.pdf уже в фикстурах).

T0-результат идёт тем же `ClaimBuilder` → claim со специфичностью `PROGRAM_INTAKE`/`INSTITUTION`, excerpt = значение из JSON-LD (честно пометить `method="jsonld"` — поле `method` в claim уже существует).

**Приоритет T0 над всеми:** если T0 дал claim нужного типа — regex и модель для этого типа на этой странице не запускаются. Это одновременно и удешевление, и точность.

## 3.2 T1 — детерминированные парсеры (текущие, починенные)

Оставить как есть, но закрыть известные дыры (из предыдущего анализа, кратко):
- `FEE_WAIVER_AVAILABLE` — проверять отрицания в строке;
- `_MONEY` — не принимать 2-значные суммы рядом с валютой как tuition (€ 15 — это не цена года);
- `is_official_domain` — суффикс-матч хоста, не подстрока URL;
- страница с `<meta name="unimatch-fixture">` вне demo — жёсткая ошибка.

T1 продолжает отвечать за «простые» случаи: их_FIXTURE_корпус и `live_shapes` — отличная регрессионная сетка для T1.

## 3.3 T2 — LLM-промпт (модель как сервис): где, как, с каким промптом

**Когда включается:** после T0+T1, если для страницы класс допускает типы claims, а T0/T1 дали покрытие < N типов (например: страница `PROGRAM_DETAIL`, а мы не получили ни `IELTS_MIN_OVERALL`, ни эквивалент, ни явный «English requirements не публикуются»). То есть **LLM достаёт то, что regex не увидел, на страницах, которые уже классифицированы**. LLM не участвует в discovery-решениях и не создаёт «новых страниц».

**Модель:** любая frontier-модель через API с JSON-mode (структурированный вывод). Абстракция — как `PaymentProvider`: интерфейс `ClaimExtractor` за `get_extractor()`, реализации `OpenAI/Anthropic/Glif/local`. Тесты — против `FakeExtractor` (детерминированный дубль, тот же паттерн, что `FakeProvider` в платежах).

**Промпт — сердце яруса.** Требования к нему:
- страница подаётся как markdown-подобный текст (BeautifulSoup → заголовки/таблицы/списки, выкидываем меню/футер — сейчас `extraction.py` уже умеет сегментировать);
- модель обязана **цитировать дословно** (`excerpt`) — верификатор это проверит;
- модель обязана отвечать `null`-ами («не опубликовано») — незнание лучше выдумки;
- выход — жёсткая JSON-схема, она же валидируется pydantic-моделью `ClaimCandidate`.

Скетч промпта (это важнейший артефакт, хранить в репо `prompts/extraction_v1.md`, версиционировать, тестировать):

```
You extract ADMISSION REQUIREMENTS from a university programme page.

RULES — breaking any rule makes your output worthless:
1. Quote VERBATIM. The `excerpt` field MUST be an exact copy of a contiguous
   span from PAGE TEXT below. No paraphrasing, no shortening, no fixing typos.
2. If the page does not state a value, output null for it. NEVER infer,
   never compute, never use your own knowledge about this university.
3. Only extract what THIS page states. Ignore navigation, footers, menus.
4. Dates must be copied exactly as written, including the year.
5. If two values conflict on the page, output BOTH as separate candidates.

PAGE METADATA: url={url}, detected_year={academic_year}, page_title={title}

PAGE TEXT:
<<<
{page_text}
>>>

Return JSON matching this schema (all fields nullable):
{
  "program_exists":        {"value": bool|null, "degree": "bachelor|master|phd|null, "excerpt": str|null},
  "ielts_min_overall":     {"value": number|null, "excerpt": str|null},
  "ielts_min_per_band":    {"value": number|null, "excerpt": str|null},
  "toefl_min":             {"value": number|null, "excerpt": str|null},
  "gpa_requirement":       {"value": str|null, "scale": str|null, "excerpt": str|null},
  "tuition_amount":        {"value": number|null, "currency": "USD|EUR|...|null",
                            "period": "year|program|null", "excerpt": str|null},
  "application_deadline":  {"value": "YYYY-MM-DD|null", "raw": str|null, "excerpt": str|null},
  "intake_open":           {"value": bool|null, "cycle": str|null, "excerpt": str|null},
  "notes_for_admissions":  {"value": str|null, "excerpt": str|null}
}
```

Пайплайн вызова:
1. `page_text` = сегментированный текст (убрать меню — иначе модель цитирует навигацию, а это уже было их FP-4);
2. ответ → `[ClaimCandidate]`;
3. каждый кандидат → верификатор (§1);
4. отклонённые → таблица `extraction_rejects` (url, claim_type, причина, версия промпта) — **это данные для обучения T3**;
5. принятые → `ClaimBuilder` → обычный путь claims.

**Стоимость:** программная страница ~6–10k токенов текста → ~$0.01–0.05 за страницу на frontier-модели; 40 кандидатов × 5 страниц ≈ $2–10 за полный live-прогон одного абитуриента. Это терпимо на старте при кэше (§5) и **должно упасть на порядок** при переходе на T3.

## 3.4 T3 — дообученная малая модель (то самое «моделька обученная»)

Это вторая стадия: сначала T2 собирает данные и доказывает ценность, потом T3 сжимает стоимость.

**Зачем:** при 300 вузах × ~50 программ × 4 страницы = 60 000 страниц, и каждый абитуриент не должен платить $5 за прогон. Дообученная 3–8B модель на self-hosted инференсе (или batch-прогоном по ночам) стоит ~$0.0002–0.002 за страницу.

**Модель-кандидат:** Qwen3-8B (или 4B для старта), tool-free, JSON-вывод, 32k контекст. Ло́ка: LoRA/QLoRA, одна GPU на несколько часов.

**Датасет — уже наполовину существует, и это уникальное преимущество проекта:**

1. **Синтетический корпус** (85 страниц) — сгенерировать программные страницы в 10× большем объёме с вариациями: 6 форматов дат, 8 форматов денег, отрицания, конфликтующие разделы, навигационный мусор. Генератор `corpus/build.py` уже есть — расширить параметризацией шаблонов. **Правильные answers известны по построению** → это готовые пары (страница → JSON) для SFT.
2. **Реальные страницы + верифицированные T2-выходы.** Каждый принятый верификатором claim от frontier-модели — это метка: (страница, claim_type, значение, дословная цитата). Накопив 5–10k таких страниц, получается датасет с распределением *реальных* форматов вузов. Отклонённые верификатором кандидаты — негативные примеры (учим модель не делать этого).
3. **Публичные параллельные корпуса** для transfer: WebFAQ / admissions-страницы из Common Crawl с ручной разметкой топ-100 страниц (одна неделя работы асессора).

**Пайплайн обучения:**
```
corpus/build.py --scale 2000        # синтетика с известными ответами
   + live_pages (сохранённые FetchResult'ы; добавить таблицу fetched_pages
     с url, content_hash, текстом — сейчас страницы не сохраняются!)
   + verified T2 outputs            # пары (текст → JSON)
        │
        ▼  формат: messages=[system, user(page_text), assistant(JSON)]
        ▼  SFT LoRA (r=16, lr 1e-4, 2-3 эпохи, 8k контекст)
        ▼  eval на канарных 10 вузах + held-out синтетике
```

**Гейты для допуска T3 в прод (жёсткие, по духу их же zero-tolerance-политики):**

| Метрика на канарном сете (10 вузов, ~200 страниц) | Порог |
|---|---|
| Верифицируемость цитат (excerpt ∈ page) | ≥ 98% |
| Точность (precision) принятых claims по ручной разметке | ≥ 95% |
| Полнота (recall) относительно T2 на тех же страницах | ≥ 90% |
| Категорические FP (утверждение, которого нет на странице) | **0** на канарном сете |
| Формат JSON валиден без retry | ≥ 99% |

Пока не прошла — T3 работает в **теневом режиме**: гоняется параллельно с T1/T2, результаты пишутся в `extraction_shadow` и сравниваются, но не попадают в claims.

**Роль модели — только экстракция.** Классификацию страниц, discovery-решения, сопоставление с профилем, ранжирование — НЕ отдавать модели: всё это детерминировано и уже хорошо работает. Это принципиально: обучаем «читателя страниц», а не «принимателя решений».

# 4. Свежесть: «брала последние-последние информации» — три контура

Принцип: **свежесть — это свойство claims, а не запуска.** Сейчас recheck уже есть, но он перечитывает всё и цепочка ломается. Перестроить так:

## 4.1 Контур A — инкрементальный обход источников (ежедневно, дёшево)

Новый воркер-джоба `source_scan` (в существующем durable queue):

1. Для каждого вуза из реестра: прочитать **robots.txt → sitemap index** (это дёшево, 1–2 запроса на вуз).
2. Из `<url><lastmod>` взять даты. **Ключевое:** сравнить с сохранённым `content_hash`/`lastmod_seen` страницы (новая таблица `source_pages`).
3. Если `lastmod` изменился ИЛИ страница входит в число «несущих» (те, откуда растут активные claims) → условный GET: `If-None-Match: <ETag>` / `If-Modified-Since` (заголовки сохранить в `source_pages` при первом чтении — `Fetcher` сейчас их не хранит, добавить).
4. `304 Not Modified` → ноль работы. Изменилось → `content_hash` (sha256 текста) отличается → положить страницу в очередь **переэкстракции только этой страницы**.
5. Sitemap без lastmod (бывает) → fallback: content-hash всех «несущих» страниц раз в N дней по freshness-окнам (см. §4.3).

Итог: ежедневный обход 300 вузов ≈ 300–600 лёгких запросов + точечные переэкстракции. Politeness (1.5 c/хост) не нарушается — это уже глобальный лимит на вуз в день.

## 4.2 Контур B — change detection → точечная переэкстракция

Новая таблица (миграция):

```python
class SourcePage(Base):
    id, url, registrable_domain, institution_key
    etag, last_modified_header
    content_hash            # sha256 нормализованного текста
    lastmod_seen            # из sitemap
    fetched_at, http_status, page_type
    active_claims           # counter — сколько живых claims от неё растёт

class ExtractionJob:  # или переиспользовать jobs с kind="reextract_page"
    source_page_id, reason  # "sitemap_lastmod" | "content_hash" | "claim_stale" | "manual"
```

Правило: **страница переэкстрагируется, а не «обновляется»** — старые claims этой страницы помечаются `SUPERSEDED` (новый статус), новые пишутся рядом. История сохраняется: можно показать пользователю «значение изменилось с X на Y 3 дня назад». Конфликты新旧 claims решаются существующим `find_conflicts` + `enforce_source_hierarchy`.

Это одновременно чинит их баг T13 (цепочка recheck умирает): recheck больше не «перезапуск стадий прогона», а точечные `reextract_page`-джобы + пересборка результатов (`_update_result` уже умеет upsert, а дубли claims чинится `_replace_evidence` — из предыдущего анализа).

## 4.3 Контур C — freshness окон по типу claim (уже есть, донастроить)

`domain/freshness.py` оставить, но:
1. Окна сделать **настраиваемыми per claim_type** через Settings (сейчас константы в коде);
2. `next_recheck_at` для пользователя считать как `min` по активным claims — уже так (`earliest_recheck`);
3. При показе шорт-листа: claim с истёкшим окном → `POSSIBLY_STALE` (есть) **+ триггер тихой догрузки** (нет): фронт при открытии строки с stale-claim дергает `POST /recheck-row/{result_id}` — точечная переэкстракция страниц этой строки, не всего прогона. UX: «перепроверяем» → обновление строки.

## 4.4 Сквозное правило показа

Любое значение в UI несёт: значение → источник (URL) → дата прочтения → статус свежести. Это уже реализовано в их claim-модели — **не трогать, только питать**. «Последние-последние» ≠ «скачали сегодня всё», а = «для каждой несущей страницы мы знаем, менялась ли она, и перечитали, если да».

# 5. Кэш и экономика: разделить «чтение вуза» и «прогон абитуриента»

Сейчас каждый live-прогон абитуриента сам читает вузы (per-worker дисковый кэш, TTL 24 ч — и воркеры не делят его). С LLM-экстракцией это ещё и деньги. Перевернуть модель:

1. **`source_pages` + `claims` — общее знание продукта** (shared, PostgreSQL), а не артефакт одного прогона. Claims уже в БД — формально отделить `claims` от `run_id` (сейчас claim привязан к run; добавить nullable `source_page_id` и «базовые» claims вне прогонов).
2. **Джоба `source_scan`** (§4.1) гоняет чтение+экстракцию вузов **без пользователя**, по расписанию и по событиям (lastmod). Результат — база claims по вузам.
3. **Прогон абитуриента** = сопоставление профиля с базой claims (мгновенно, уже всё вычитано) + **точечная догрузка** только того, чего в базе нет/протухло (его специфические программы, если каталог расширился).
4. LLM-вызов кэшируется на уровне `(content_hash, prompt_version)` — одна и та же версия страницы не экстрагируется дважды.

Экономика: 300 вузов × 50 страниц × $0.02 (T2) ≈ $300 на первичную базу + $10–30/мес на инкрементальные обновления. После T3 — в разы дешевле. Прогон абитуриента — почти бесплатен и **мгновенен** (сейчас live-прогон — десятки минут; станет секундами, что меняет UX продукта целиком: «первый результат за вечер» → «первый результат за 30 секунд»).

Politeness при этом даже улучшается: теперь мы читаем вуз один раз в день по расписанию, а не «сколько абитуриентов — столько прогонов».

# 6. Evaluation: как доказывать, что поиск стал лучше (и не сломался)

В духе их канарной культуры, формализовать:

**6.1 Канарный сет (уже есть `scripts/canary_discovery.py`)** — расширить до трёх наборов:
- `canary_discovery`: 10 вузов, метрики: category recall (цель ≥ 26/30 держать), **program recall (цель ≥ 7/10, сейчас 1/10)**;
- `canary_extraction`: ~200 размеченных вручную страниц (значения собраны человеком с страницы) — precision/recall по каждому claim_type; zero-tolerance: категорический FP = красный гейт;
- `canary_freshness`: фикстуры, где страница «меняется» (в тесте подменяем текст) → источник переэкстрагируется, claim суперседится, конфликт отображается.

**6.2 Теневой режим новых экстракторов.** Любой новый ярус (T2, потом T3) сначала `shadow`: гоняется параллельно, расхождения пишутся в отчёт, неделю смотрим, потом включаем с флагом `UNIMATCH_EXTRACTOR_TIERS=0,1,2`.

**6.3 Регресс на фикстурах.** Каждый реальный FP из live → новая фикстура в `tests/fixtures/live_shapes/` (у них так уже делается) + при переходе на LLM — эти же фикстуры гоняются против промпта (FakeLLM в CI, реальный LLM — nightly-джоба с малым бюджетом).

**6.4 Метрики в `/metrics`** (инфраструктура есть): `extraction_tier_total{tier}`, `extraction_reject_reason_total{reason}`, `source_scan_pages_changed`, `program_recall_canary`, `claim_age_days` histogram.

# 8. Ответы на прямые вопросы «а как именно»

**«Чтобы моделька была обученная»** — да, но в правильном месте и с правильной ролью:
- обучаем **экстрактор значений со страниц** (SFT на Qwen3-4/8B, LoRA), а не «поисковик» и не «советчик»;
- данные для обучения — синтетический корпус (генератор уже есть, у него известные ground-truth ответы) + верифицированные выходы frontier-LLM на реальных страницах + фикстуры FP;
- выпуск в прод — только через теневой режим и жёсткие гейты (98% верифицируемость цитат, 0 категорических FP);
- **модель никогда не пишет в базу напрямую** — только через детерминированный верификатор.

**«Чтобы брала последние-последние информации»** — да, тремя механизмами:
- sitemap `lastmod` + ETag/Last-Modified + content-hash → **знаем, что страница изменилась**, в тот же день;
- точечная переэкстракция только изменённых страниц, старые claims → `SUPERSEDED` (история изменений сохраняется и показывается);
- freshness-окна по типу значения (дедлайн — 30 дней, tuition — 120) + перечитывание по требованию при открытии строки пользователем.

**«Правильно короче»** — правильно = каждый шаг проверяем:
- любое значение = claim с URL, дословной цитатой (машина проверила, что цитата есть на странице), датой, статусом свежести;
- любое незнание = явное UNKNOWN, а не догадка модели;
- любые изменения = наблюдаемая история (было X 1 сентября, стало Y 5 сентября);
- всё это уже встроено в продукт — новый поиск лишь наполняет эту систему быстрее, дешевле и полнее.

**Главный сдвиг парадигмы:** сейчас «прогон абитуриента = краул». Должно стать: «фоновая база знаний по вузам, обновляемая ежедневно» + «прогон абитуриента = мгновенное сопоставление + точечные догрузки». Это меняет скорость продукта на два порядка и одновременно снижает нагрузку на сайты вузов.
