# Ревью дизайна «Поиск 2.0» (ПОИСК-2.0-дизайн.md) против кода @ 4d2125c

Дата: 2026-09-07. Ревьюер: главный агент (диспетчер), проверка фактологии по исходникам.

## Вердикт

Дизайн **принимается как план работ** для live-контура (кандидат в реализацию этапов 2–3 брифа
с изменённой архитектурой: ярусы экстракции под верификатором вместо ResearchAgent-Protocol).
Фактология о текущем коде подтверждена. Спринт 1 не требует LLM-ключей → не блокирован решением
«ключей нет». Перед стартом: T16 (egress/browser hardening) — жёсткая предпосылка; масштабный
канар (19→60+ вузов) требует отдельного разрешения владельца (ранее одобрен ONE bounded run).

## Существенное совпадение с брифом (не конфликт, а конвергенция)

- Верификатор кандидатов (§1 дизайна) ≈ excerpt-валидатор из брифа [1.2]: те же правила
  нормализации и дословной подстроки. Реализуется один модуль (`domain/claim_verifier.py`),
  он же закрывает [1.2].
-Privacy-режимы промптов, FakeExtractor по образцу FakeProvider, prompt_version в ключе кэша —
  те же решения, что [2.1] брифа. Гейт `UNIMATCH_LLM_DATA_POLICY_ACK` из брифа обязателен и тут.
- Дизайн **не заменяет** этап 1 брифа целиком: ResearchAgent-Protocol можно натянуть на ярусы,
  но решение «делать ли Protocol» — владельцу; минимум — не строить оба каркаса параллельно.

## Пробелы и риски, которые дизайн не закрывает (добавить в карточки)

1. **T16-предпосылка** (см. выше) + PII-гвард на redirect-хопах (аудит: `find_pii` не вызывается
   на хопах) — до масштабирования walker'а.
2. **Политeness при 300 вузах/день**: source_scan обязан идти через единый Fetcher с Crawl-delay;
   XHR-перехват браузерного тира должен уважать robots страницы-источника.
3. **Retention для source_pages**: ResponseCache не эвиктируется (аудит) — та же ошибка повторится
   с хранением текстов страниц; нужна политика хранения/сжатия.
4. **SUPERSEDED × conflicts**: тест, что superseded-claims не учитываются в find_conflicts и
   не дублируют evidence (симптом дублей из аудита runner).
5. **Процесс**: карточки в формате crew (4+ роли, security обязателен — внешние запросы, деньги
   на T2, конкуренция джоб), заморозка контракта таблиц/статусов до кода.
6. **Канар-масштаб**: любые прогоны по новым вузам вне demo — только с явного разрешения
   владельца (одобрен один bounded NU-run; 19→60 — новое решение).
7. **T3-обучение**: на этой машине нет GPU/Docker; SFT — облако/отложенный этап, гейты §3.4
   принять как есть (0 категорических FP — совместимо с zero-tolerance продукта).

## Рекомендуемый порядок

0. T16 (egress + browser hardening) — предпосылка, уже в очереди.
1. Спринт 1 дизайна как карточка-эпос: source_pages + ETag/content-hash, claim_verifier,
   фиксы T1, catalog_walker, замер program recall на 10 канарных вузах (разрешение владельца).
2. Спринт 2: T2 shadow-режим (нужны ключи — к тому моменту решение владельца), source_scan,
   точечный refresh строки.
3. T26 сузить до News-слоя (SourceChange забирает дизайн); T25 понизить до P2/заморозить.
