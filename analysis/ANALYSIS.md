# ASHYQ Apply — аудит алгоритма подбора университетов

*Team-lead review, 2026-09-05. Репозиторий: github.com/wpalish/ashyq-apply (77 коммитов, ветка main).*
*Все цифры ниже получены на реальном прогоне демо-пайплайна, скрипты — в `analysis/scripts/`.*

---

## 1. Что это за проект

**ASHYQ Apply** (внутреннее имя пакетов — `unimatch`) — сервис шортлиста университетов и стипендий для
иностранных абитуриентов, в первую очередь из Казахстана. Отвечает на один вопрос:
*«куда я могу поступить и кто из них реально за это заплатит?»*

| Слой | Стек | Размер |
|---|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL/SQLite, httpx, BeautifulSoup, Playwright | ~90 файлов, 785 тестов, покрытие 92 % |
| Frontend | React + TypeScript + Vite, 12 экранов | 120 unit + 63 e2e (Playwright) |
| Данные | Demo-корпус: 40 синтетических кандидатов (16 с полными страницами). Live-реестр: **10 университетов** в 8 странах | — |

**Философия продукта — «evidence-first»:** каждое число на экране ссылается на официальную страницу,
цитату и дату. Система принципиально *не предсказывает* шанс поступления, не конвертирует оценки молча,
не превращает «неизвестно» в догадку. Это сильная и редкая сторона проекта — её нужно сохранить при
любой переделке алгоритма.

**Пайплайн (state machine, 6 стадий, `pipeline/runner.py`):**

```
 profile ──► 1.validate ──► 2.discover ──► 3.verify ──► 4.funding ──► 5.assess ──► user ──► 6.documents
                              (кандидаты)   (страницы    (стипендии)   (eligibility,   decision
                                             программ,                  fit, score)
                                             цены, гос.
                                             правила)
```

Зрелость: инфраструктура (очередь, auth, tenancy, миграции, метрики, бэкапы) — уровень production-candidate.
Сам **подбор** — уровень прототипа. Ниже почему.

## 2. Как устроен подбор сейчас — три слоя

### Слой A. Discovery — откуда берутся кандидаты
`adapters/discovery/fixture_discovery.py` (demo) / `live_discovery.py` (live)

```
для каждой строки каталога:
    country ∈ excluded_countries          → выбросить            (жёсткий фильтр)
    программы: substring(intended_field, program.field)
               AND program.degree == level → оставить программу
    (если в каталоге программы есть, а ни одна не подошла → выбросить вуз)
сортировка: (страна в preferred? 0:1,  есть официальная страница? 0:1,  лучший ranking,  имя)
срез:       первые candidate_limit=40  →  из них verify_limit=20 идут на верификацию
```

**Что важно:** климат, размер города, размер вуза, тип кампуса, нагрузка, бюджет — **не участвуют** в
discovery вообще. Срез до 20 верифицируемых происходит *до* того, как мягкие предпочтения хоть на что-то
повлияли. В live-режиме «поиска» нет как класса: перебираются 10 захардкоженных вузов из
`institution_registry.json`.

### Слой B. Eligibility — жёсткие требования
`domain/eligibility.py` — сравнение профиля с извлечёнными claim'ами: GPA (только при совпадении шкалы),
IELTS overall + каждый sub-band, TOEFL, SAT/ACT, дедлайн, открыт ли набор, обязательные предметы.
Статусы: `MET / PENDING / GAP / NEEDS_OFFICIAL_CLARIFICATION`. Hard-filter срабатывает только на
*подтверждённое* требование, которое абитуриент *подтверждённо* не выполняет.

**Оценка: это сделано хорошо.** Логика асимметрий (отсутствие данных не отсеивает) — правильная. Трогать
не нужно.

### Слой C. Scoring — ранжирование
`domain/scoring.py :: score_result()` — **взвешенная аддитивная сумма** 13 компонент × штраф за пропуски.

| Компонента | Вес по умолчанию | Откуда raw ∈ [0,1] |
|---|---|---|
| Academic fit | 1.0 | статус eligibility: MET=1.0, PENDING=0.6, GAP=0.15 |
| Funding fit | 1.5 × criticality | класс стипендии: CONFIRMED=1.0 … NOT_ELIGIBLE=0 |
| Affordability | 0.75 × criticality | gap / потолок семьи: ≤1 → 1.0; иначе 1.5−ratio/2 |
| Country preference | 1.0 | preferred=1.0, none=0.5, other=0.3, excluded=0 |
| Programme standing | 0.8 | ranking vs target band |
| Extracurricular | 0.6 | **только из профиля** — одинаково для всех вузов |
| Career / Post-study work | 0.7 / 0.5 | есть текст? 0.8 : missing |
| City / Climate / Workload / Size / Campus | 0.4 / 0.3 / 0.3 / 0.3 / 0.3 | лейбл strong=1.0, good=.75, acceptable=.5, weak=.25 |
| **max_possible** | **≈ 8.45** | |

```
total = Σ raw_i · w_i  ×  (1 − min(0.25, 0.03 · #пропусков))
```

Лейблы fit (`_fit_label` в runner.py) — расстояние по «лестнице»: climate = [cold, temperate,
mediterranean, warm]; совпадение → strong, соседняя ступень → good, через одну → acceptable, дальше → weak.
Лейблы **вычисляются один раз на стадии verify и замораживаются** в `ProgramResult`.

Дополнительно считается `admissions_fit` (STRONGER / PLAUSIBLE / AMBITIOUS / INSUFFICIENT_DATA) по
среднему запасу над опубликованными минимумами + сила активностей — **но в score он не входит**, только
показывается.

## 3. Экспериментальная проверка: подбор действительно не работает

### 3.1. Результат демо-прогона (профиль: CS bachelor, KZ, IELTS 7.0/W6.0, бюджет 6 000 USD, climate=temperate)

| # | Университет | Elig | Funding | Остаток в год | Score |
|---|---|---|---|---|---|
| 1 | **UBC (Канада)** | MET | FULL_TUITION | **21 471 USD** | 6.54 |
| 2 | Groningen | PENDING | FULL_RIDE_CONFIRMED | 1 848 USD | 6.39 |
| 3 | Aalto | MET | FULL_TUITION | 11 859 USD | 6.18 |
| 4 | TU Delft | **GAP** | FULL_RIDE_CONFIRMED | 2 446 USD | 5.93 |
| 5 | KU Leuven | MET | FULL_TUITION | 7 554 USD | 5.92 |

Семья заявила `max_acceptable_gap = 6 000 USD`, `funding_criticality = decisive`. **Первое место занял
вариант с недостачей в 3,6× больше допустимой.** Affordability для UBC = 0.00 — но funding_fit дал 1.5,
academic 1.0, country 1.0, и сумма всё перекрыла. Это главный симптом аддитивной модели: критический
провал компенсируется мелкими плюсами.

### 3.2. Чувствительность к климату (`03_climate_sensitivity.py`)

Пересчитал лейблы и score для climate = temperate / warm / cold при прочих равных:

| | temperate | warm | cold |
|---|---|---|---|
| Top-5 | UBC, Groningen, Aalto, Delft, Leuven | **тот же** | **тот же** |
| Макс. сдвиг score одного вуза | — | 0.146 (**1.7 %** от max) | 0.08 |

Климат при весе 0.3 может сдвинуть score максимум на 0.27 из 8.45 (3 %). Порядок топ-5 не меняется
ни при каком климате. Даже при весе климата 3.0 и обнулённых academic/funding топ-1 остаётся UBC.
**Пользователь честно заполняет «климат», а результат на него не реагирует.** То же — city_size, size,
campus, workload.

### 3.3. Чувствительность discovery к полю (`01_discovery_sensitivity.py`)

| intended_fields | Кандидатов | Верифицируемых |
|---|---|---|
| `computer science` | 40 | 16 |
| `Computer Science` | 40 | 16 |
| `cs` | 24 | **0** |
| `informatics` | 24 | **0** |
| `medicine`, `mechanical engineering` | 24 | **0** |
| level = master | 24 | **0** |

Matching — подстрока без синонимов, без таксономии. Любое отклонение от точной фразы каталога →
0 верифицируемых вузов, 24 «лида из каталога без страниц». В live-режиме matching по URL/тексту ссылок
(`matches_field`, слова длиннее 3 букв) — та же проблема.

### 3.4. Прочие дефекты алгоритма (из кода)

| # | Дефект | Где | Следствие |
|---|---|---|---|
| D1 | Extracurricular считается только из профиля | `scoring.py::_activity_strength` | Константа для всех строк → 0 различающей силы, но занимает 0.6 веса (7 % шкалы) |
| D2 | Fit-лейблы заморожены на стадии verify | `runner.py:401–425` | Смена предпочтений = повторный краулинг (минуты в live) вместо мгновенного re-rank |
| D3 | `admissions_fit` не входит в score | `scoring.py` | Вуз «на грани минимумов» и вуз «с запасом 20 %» получают одинаковый Academic=1.0 |
| D4 | Штраф за пропуски — мультипликативный на всю сумму | `scoring.py:337` | Наказывает вузы с плохо парсящимися сайтами, а не худшие вузы; смешивает «насколько подходит» с «насколько мы уверены» |
| D5 | Rank-компонента `1 − rank/1000` без target | `scoring.py` | Линейная шкала: #50 vs #100 разница 5 %, но #500 vs #900 — 40 %; обратная реальной чувствительности |
| D6 | Нет портфельной логики | — | Топ-20 может быть 20 «reach»-вариантов; понятия safety/match/reach нет |
| D7 | Срез до 20 до учёта предпочтений | `runner.py:_stage_verify` | При богатом каталоге подходящие по климату/бюджету вузы просто не дойдут до верификации |
| D8 | 12 слайдеров весов 0–3 | `ScoringWeights` + PreferencesScreen | Пользователь не может осмысленно выставить 12 весов; на практике все остаются дефолтными |
| D9 | Словарь атрибутов уже реестра формы | `PROFILE_FIELDS.md` | `size=small`, `campus=suburban` — не могут дать strong никогда |

### 3.5. Корневая причина

> **Подбор не работает не потому, что формула плохая, а потому что нет трёх вещей: (1) вселенной
> вузов, в которой можно искать; (2) нормального сопоставления направлений; (3) неаддитивной агрегации,
> где критичные факторы (бюджет, eligibility) не компенсируются косметикой.** Формула — четвёртый пункт.

## 4. Какой алгоритм подошёл бы лучше

Предлагаю разделить «подбор» на четыре независимых слоя. Каждый можно тестировать и заменять отдельно;
это ложится на существующую архитектуру (`domain/` без I/O, `adapters/` с I/O).

```
┌────────────────┐   ┌─────────────────┐   ┌──────────────────┐   ┌─────────────────┐
│ 1. UNIVERSE    │──►│ 2. RETRIEVAL    │──►│ 3. RANKING       │──►│ 4. PORTFOLIO    │
│ каталог вузов  │   │ hard-фильтры +  │   │ утилиты по осям  │   │ reach/match/    │
│ × программ с   │   │ таксономия      │   │ + неаддитивная   │   │ safety, диверси-│
│ атрибутами     │   │ направлений +   │   │ агрегация +      │   │ фикация, объяс- │
│                │   │ pre-score       │   │ отдельная        │   │ нение           │
│                │   │                 │   │ «уверенность»    │   │                 │
└────────────────┘   └─────────────────┘   └──────────────────┘   └─────────────────┘
      данные              recall               precision            польза
```

### Слой 1. Universe — структурированный каталог (это data-задача, а не алгоритмическая)

Без вселенной в 500–3 000 вузов любой алгоритм ранжирует 10 строк. Источники, совместимые с
принципом «ничего из профиля не уходит наружу» (каталог строится оффлайн, один раз):

- **ROR** (Research Organization Registry) + **Wikidata** — открытые, ~100k организаций: страна, город,
  координаты, число студентов, год основания, домен сайта.
- **QS / THE / ARWU** — таблицы рейтингов (уже есть адаптер `fixture_rankings`).
- **Климат — вычислять, а не размечать руками:** по координатам вуза берём класс **Köppen–Geiger**
  (открытый растр) → маппинг в {cold, temperate, mediterranean, warm, tropical}. Объективно, проверяемо,
  масштабируется на тысячи вузов. Это же снимает вопрос «а кто решил, что Гронинген temperate».
- **city_size** — по населению города из Wikidata (пороги ≤300k / ≤1M / ≤3M / >3M).
- **size** — по числу студентов (≤10k / ≤25k / >25k).
- Стоимость/дедлайны/стипендии — **по-прежнему только из официальных страниц** (evidence-first не
  ломаем): каталог даёт *кандидатов и мягкие атрибуты*, верификация даёт *факты*.

### Слой 2. Retrieval — из вселенной в кандидаты

1. **Таксономия направлений — ISCED-F 2013** (UNESCO, 4-значные коды: 0613 = Software & applications
   development, 0612 = Database & network design, 0688 = Inter-disciplinary ICT…). Профиль и программы
   каталога маппятся в коды; словарь синонимов/аббревиатур (cs, informatics, computing, информатика,
   Informatik → 061x). Сравнение по иерархии: совпал 4-значный код → 1.0, 3-значный → 0.7, 2-значный
   → 0.4. Опционально — эмбеддинги названий как fallback для «длинного хвоста».
2. **Hard-фильтры (knockout):** degree level, excluded countries, язык обучения, дедлайн прошёл
   (подтверждённо), подтверждённый hard-filter из eligibility, `requires_full_ride` при отсутствии
   таких стипендий (если подтверждено).
3. **Pre-score по атрибутам каталога** (ещё без краулинга): страна, климат, размер, ranking band,
   ориентировочная стоимость (tuition band из каталога — помечена как *unverified*). Срез в
   `verify_limit` делается **по pre-score**, а не по «страна + рейтинг». Тогда предпочтения решают,
   *кого вообще проверять*.

### Слой 3. Ranking — неаддитивная агрегация с сохранением объяснимости

Три принципа:

**(a) Разделить «факты» и «суждения».** Сейчас fit-лейблы и score лежат внутри `ProgramResult` рядом
с claim'ами. Нужно: claim'ы — неизменяемы после краулинга; всё, что зависит от предпочтений
(лейблы, утилиты, score, портфель) — чистая функция `rank(results, profile)`, вызываемая по кнопке
без повторного краулинга. Это делает смену климата *мгновенной*.

**(b) Утилиты по осям u_i ∈ [0,1] ∪ {unknown}** — как сейчас, но:
- affordability: плавная кривая с *обрывом* — ratio ≤ 1 → 1.0; 1–1.5 → линейно до 0.3; > 1.5 → 0.05
  (не 0, чтобы геометрика не схлопнула в ноль на округлении, но фактически вето);
- academic: использовать `admissions_fit` (запас над минимумами), а не только статус;
- ranking: логарифмическая шкала `u = 1 − log(rank)/log(2000)` вместо линейной;
- extracurricular — **убрать из score вузов** (константа) и перенести в портфельную классификацию
  reach/match (где он по смыслу и нужен: сильные активности → можно позволить больше reach).

**(c) Агрегация — взвешенное геометрическое среднее по известным осям:**

```
fit(u) = exp( Σ_{i известно} w_i·ln(max(u_i, ε)) / Σ_{i известно} w_i ),   ε = 0.05
coverage = Σ_{i известно} w_i / Σ_all w_i                                  ← отдельное число
```

Почему геометрика, а не сумма: она **некомпенсаторна** — u_affordability = 0.05 утянет fit к ~0.1–0.2
независимо от остальных, и UBC из примера выше уйдёт вниз, где ему и место. При этом каждая компонента
остаётся видимой в объяснении (принцип «не чёрный ящик» сохраняется), а в логарифмическом пространстве
это по-прежнему взвешенная сумма — понятно и тестируемо.

Альтернативы, которые тоже рассматривал (сравнение в разделе 5): лексикографические ярусы,
TOPSIS/ELECTRE с порогами вето, Pareto-фронт, learning-to-rank.

**(d) Неизвестное — не штраф, а отдельная метрика.** `coverage` показывать рядом со score
(«подходит на 0.82, подтверждено 60 % факторов») и дать сортировку по обеим. Это честнее текущего
`×(1−0.03·n)`: score отвечает на «насколько подходит из того, что знаем», coverage — «насколько мы
уверены». Если продуктово нужно, чтобы «неполные» стояли ниже — сортировать по `fit × coverage^γ`
с явным γ, а не прятать это внутрь score.

### Слой 4. Portfolio — из отсортированного списка в шортлист

Абитуриенту нужен не топ-20 по одному числу, а сбалансированный набор:

```
категория по (admissions_fit × funding_fit):
   safety : STRONGER_FIT  и funding ∈ {CONFIRMED}
   match  : PLAUSIBLE/STRONGER и funding ∈ {CONFIRMED, COMPETITIVE}
   reach  : AMBITIOUS или funding = LIMITED
   unknown: INSUFFICIENT_DATA / UNKNOWN   → отдельная секция «нужно уточнить»

шортлист N=10: ≥2 safety, ≥4 match, ≤3 reach; ≤3 вуза на страну; внутри категории — по fit.
```

Квоты — параметры, не константы. Это то, что делает живой консультант, и это объяснимо одной фразой.

### Веса — как их получать от пользователя (D8)

12 слайдеров заменить на ранжирование 5–6 приоритетов drag-and-drop («что важнее: бюджет, страна,
рейтинг, климат, карьера, размер города») → rank-order centroid weights (ROC): w_k = (1/n)·Σ_{j≥k} 1/j.
Расширенный режим со слайдерами оставить под спойлером. Это отдельная задача фронта, в первую итерацию
можно не брать.

## 5. Сравнение вариантов агрегации

| Вариант | Некомпенсаторность | Объяснимость | Реализация | Риск |
|---|---|---|---|---|
| Текущая взвешенная сумма + штраф | нет | высокая | есть | критичные провалы маскируются (UBC #1) |
| **Сумма + вето-пороги** (если critical u_i < τ → cap total) | частичная | высокая | 1 день | пороги произвольны, ступенчатость |
| **Взвешенная геометрика** (рекомендую) | да, плавная | высокая (в log-пространстве — та же сумма) | 1–2 дня + миграция тестов | нужен ε; менее интуитивна на первый взгляд |
| Лексикографические ярусы (eligibility → бюджет → предпочтения) | полная | очень высокая | 1 день | слишком жёстко: 1 USD разницы бюджета важнее любого климата |
| TOPSIS / ELECTRE с вето | да | средняя | 3–4 дня | тяжело объяснить пользователю «расстояние до идеала» |
| Pareto-фронт + выбор пользователя | не нужна | высокая | 2–3 дня | при 8 осях фронт = почти всё |
| Learning-to-rank по approve/reject | — | низкая | недели | нет данных; противоречит «не предсказываем» |

Комбинация, которую предлагаю как целевую: **hard-фильтры → геометрика с ε → coverage отдельно →
портфель**. Она удовлетворяет всем «честным» правилам проекта: unknown ≠ 0, ничего не предсказывает,
каждая компонента видна.

- `eligibility.py`, `funding.py`, `costs.py`, `conflicts.py`, `freshness.py` — качественно, с тестами,

- Принцип «claim с источником» — не ослаблять. Каталожные атрибуты (климат, размер) помечать как
  `catalog-derived`, а не как verified-claim.
- Все существующие тесты на объяснимость (`test_every_component_names_its_weight_and_its_reason` и др.)
  должны пройти после замены агрегации — это критерий приёмки.
