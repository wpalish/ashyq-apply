## Existing batch support and exact caveat

Core controller accepts sequential `plan.actions` lists and writes per-item raw hashes, ordering and counters, checking caps and the wall before I/O. Journal schema and parent still allow one next action. This is **not a drop-in safe batching contract**: controller.py:708 only refuses another search_provider after 402/429; a later fetcher in a mixed list is not covered by that condition. Current V12 reads its one-action tail and latches shared STOP before another workflow. A future batch must stop before EVERY later item, retain sequential source requests, and admit no unverified/postdeadline evidence.

Adaptive discovery stays sequential: a new search result must be seen in saved returned source before a later content-dependent fetch. A general query plus a previously known independent candidate is different from such dependent discovery. Existing `history[-2:]`, per-turn4/2 bounds and whole-prefix processed markers also need explicit handling so batches do not hide or falsely acknowledge unprocessed sources.

## Narrow prospective options

1. Amortize workflow transport while keeping one controlled proposal at a time and validating each original raw tail before the next adaptive proposal.
2. Alternatively introduce a small, declared sequential batch for already-known independent candidates, with shared refusal STOP before each item and complete per-item replay/proof.
3. Generate public question prose from the exact target rules, add a source-only programme ambiguity rule, and make bootstrap navigation-only when no source exists.

Each option requires a prospective version/write-ahead and synthetic replay/isolation/STOP tests. Preserve Exa,60 reads/6 queries, immutable900 s, normal default reasoning, current-case blinding, literal scope/nulls, typed values, all exact quote/coordinate proof and local validators. No current V12 helper, selector, stage, workspace, clock or proof changes are proposed.
